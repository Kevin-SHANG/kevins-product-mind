# Kevin's Product Mind

[中文](README.md) · [English](README.en.md) · **한국어**

**중국 대형 인터넷 기업의 제품 방법론을 담은 PM용 Agent Skill입니다. 모호한 요구를 근거 있는 제품 판단으로 바꾸고, 리뷰와 개발에 바로 쓸 수 있으며 프로토타입과 맞아떨어지는 PRD로 작성합니다. 시장과 언어에 관계없이 쓸 수 있습니다.**

요구 정리, 방안 비교, 프로토타입 대조, 범위 관리, PRD 작성을 하나의 흐름으로 다룹니다. 정보가 부족하면 추천 방향과 핵심 공백을 먼저 제시하고, 요구가 확정되면 바로 작성합니다. 여러 단계나 세션에 걸친 작업은 기능 분해, 규칙 기준선, 프로토타입 대조, 모듈별 작성 순서로 진행하며, 단계마다 결과를 파일에 남겨 모델의 기억에 기대지 않습니다.

## 주요 기능

| 상황 | 주요 산출물 |
| --- | --- |
| 아이디어·피드백·요구가 아직 불명확함 | 요구 브리프, 추천안, 주요 트레이드오프, 확인 필요 항목 |
| 핵심 방안과 이번 범위가 확정됨 | PRD, 기능 규칙, 주요 흐름, 예외 처리, 검수 기준 |
| 프로토타입이 이미 있음 | 페이지 매핑, 상태 매트릭스, 규칙·프로토타입 행 단위 대조표, 프로토타입 문제 목록, 그리고 프로토타입과 일치하는 PRD |
| 프로토타입을 먼저 만들어야 함 | 프로토타입 청사진(페이지 목록, 상태 매트릭스, 화면 형태, 문구, 금지 항목). 확인 후 화면 제작 |
| 단계·세션을 넘나드는 큰 요구 | 기능 분해, 결정 기준선, 단계 마감 점검, 인수인계 템플릿. PRD는 회차마다 모듈 하나씩 전달 |
| 기존 방안 수정·리뷰 | 범위 내 수정, 업무 로직 문제와 구체적 제안 |
| 기획과 검증 | MVP, 우선순위, Roadmap, 지표 정의, 실험 설계 |

작성 원칙은 조건과 처리, 규칙의 단일 정의 위치, 입력부터 화면 필드까지의 연결, 제품 규칙과 기술 구현의 경계입니다. PRD는 무엇보다 사람이 읽는 문서입니다. 독자는 하나의 사용자 과업을 처음부터 끝까지 따라 읽을 수 있어야 하고, 삭제 범위처럼 여러 모듈에 걸친 정책은 표 하나로 모읍니다. 사실, 가정, 미지수, 실제 0은 구분하며, 예시 데이터나 검증되지 않은 효과를 현재 약속처럼 쓰지 않습니다.

단순 전사, 번역, 형식 변환, 이미 확정된 방안의 코드 구현은 주요 용도가 아닙니다. 사용자의 템플릿, 작성 샘플, 현재 작업 범위는 여전히 중요한 입력입니다.

Skill과 참고 자료는 중국어로 작성되어 있으며, 요구에서 출력 언어를 지정할 수 있습니다. 영어·한국어 README는 저장소 설명과 요청 템플릿의 번역이며, 다른 언어에서의 효과는 실제 클라이언트에서 확인해야 합니다.

## V5 업데이트

V5는 재구성 버전으로, V3이 '프로토타입 단계'와 '완전한 PRD 단계'에서 드러낸 문제를 다룹니다. 프로토타입과 PRD가 맞지 않고, 단계 사이에 확정된 결정이 사라지고, 검수가 개수만 세고 읽히는지는 보지 않던 문제입니다.

**V5.0.1**

- **논리 서술**: 실제 PRD를 참고해 조건, 흐름, 상태를 단계별 들여쓰기 목록으로 작성하고 한 문단에 몰아 쓰지 않습니다. 예시 문서도 함께 보완했습니다. 한 문장으로 끝나는 공용 규칙은 쓰이는 자리에 그대로 다시 씁니다.
- **진행 방식**: 프로토타입을 보고 PRD 전체를 쓸 때만 단계별로 진행하고, 작은 수정은 한 번에 끝냅니다. 전체를 한 번에 써 달라는 요청도 가능하지만, 모듈마다 먼저 개별 점검한 뒤 합칩니다.
- **점검**: 프로토타입을 보고 PRD를 쓸 때는 프로토타입에 쓰인 소재를 목록으로 정리하고, 주요 흐름을 처음부터 끝까지 직접 확인합니다.

**V5.0.0**

- **프로토타입 대조**: `references/prototype.md` 추가. 프로토타입이 입력되면 페이지 매핑, 상태 매트릭스, 행 단위 대조표 두 장을 먼저 만든 뒤 PRD를 씁니다. 화면에서 보이는 상호작용은 구체적인 페이지를 참조하고, 보이지 않는 규칙은 본문에 씁니다. 화면 안의 임시 설명, 예시 데이터, 선택해도 차이가 없는 버튼은 프로토타입 문제로 보고하며 제품 규칙으로 쓰지 않습니다.
- **장기 진행**: `references/long-project.md` 추가. 단계별 요구는 기능 분해부터 시작하고, 확정된 결정은 그 회차에 결정 기준선에 기록하며, 작업 전에 파일을 다시 읽습니다. 단계 마감 점검, 파일 기반 인수인계, 기능 라인별 서브 에이전트 분담을 지원합니다.
- **조용한 덮어쓰기 금지**: 기록된 결정과 충돌할 때, 명확한 변경은 바로 반영하고 기록하며, 의도가 불분명할 때만 묻습니다. 같은 확인을 반복하지 않습니다.
- **가독성과 통합의 균형**: 규칙의 형태에 따라 쓰는 방식을 정합니다. 한 과업에만 속한 규칙은 그 자리에 쓰고, 한 문장짜리 공용 규칙은 쓰이는 곳마다 그대로 다시 쓰며, 여러 대상과 상황을 대조해야 하는 정책은 표 하나로 모읍니다.
- **정직한 검수**: 개수, 매핑, 문법 통과로는 흐름이 실제로 이어지는지, 문서가 읽히는지 증명할 수 없습니다. 선형 가독성, 통합, 표현 일치에 대한 양방향 점검을 추가했습니다.

자세한 내용은 [V5.0.1 릴리스 노트](https://github.com/Kevin-SHANG/kevins-product-mind/releases/tag/v5.0.1)와 [V5.0.0 릴리스 노트](https://github.com/Kevin-SHANG/kevins-product-mind/releases/tag/v5.0.0)를 참고하세요.

## 설치

최신 V5.0.1 패키지를 다운로드하여 압축을 풀고, `SKILL.md`가 포함된 폴더 전체를 클라이언트에 설정된 스킬 디렉터리에 넣되 폴더 이름은 `kevins-product-mind`로 유지하세요.

예를 들어 `~/.codex/skills`를 스킬 디렉터리로 쓰는 경우 최종 진입점은 `~/.codex/skills/kevins-product-mind/SKILL.md`입니다. 다른 디렉터리를 쓴다면 경로를 바꾸세요. 대상 폴더가 이미 있으면 직접 수정한 내용을 먼저 보관한 뒤 업데이트하고, 클라이언트 안내에 따라 스킬을 다시 불러오거나 새 세션을 시작하세요.

아래에서 설명하는 Skill, 참고 자료, 요청 템플릿, 스크립트는 모두 설치 패키지에 들어 있습니다.

## 요청 템플릿

`需求提示词.md`의 새 요구 템플릿을 번역한 것입니다. 아는 정보만 채우고, 모르는 항목은 비워 두어도 됩니다.

```text
$kevins-product-mind를 사용해 다음 제품 요구를 도와주세요.

요구: [어떤 문제를, 누구를 위해 해결하려는가]
배경과 자료: [현재 상황, 사용자 피드백, 데이터, 문서 또는 링크]
기존 프로토타입: [위치. 없으면 비워 두세요. 화면과 규칙이 충돌할 때 무엇을 우선하는지]
확정된 사항과 제약: [반드시 유지할 규칙, 이번에 하지 않을 내용]
진행 방식: [한 번에 작성 / 단계별 진행]
원하는 산출물: [방안 제안 / MVP / PRD / 방안 리뷰 / 기타]

먼저 자료를 읽고 판단을 제시해 주세요. 정보가 충분하면 바로 완성하고, 방향이나 정확성에 영향을 주는 핵심 공백은 한 번에 모아서 질문해 주세요. 그 밖의 위험이 낮고 되돌릴 수 있는 세부 사항은 직접 판단해 주세요. 이미 정한 결정은 다시 확인하지 말고, 가정과 사실을 구분하며, 이번 범위를 넓히지 마세요.
```

같은 파일에는 컨텍스트를 압축하거나 새 세션을 열 때 쓰는 '단계 인수인계' 템플릿도 있습니다. 현재 단계, 기준 파일, 첫 작업, 하지 말아야 할 일을 다음 세션에 넘깁니다.

다른 출력 언어가 필요하면 템플릿 뒤에 요청을 덧붙이세요. `$skill-name` 호출 지원 여부는 클라이언트에 따라 다르며, 자동 로딩이 안 되면 `SKILL.md`와 해당 작업에 필요한 참고 자료를 직접 제공하세요. 이 방식의 로딩과 실행 결과는 클라이언트에 따라 다릅니다.

| 파일 | 용도 |

| `SKILL.md` | 진입점, 제약, 참고 자료 라우팅 |

| `references/prd-structure.md` | PRD 구조, 흐름, 필드, 업무 규칙 |
| `references/prd-style.md` | 명명, 문체, 전달 전 점검 |
| `references/prd-cases.md` | 수정 전후 사례와 적용 범위 |
| `references/diagram-layout.md` | 다이어그램 배치, 연결선, 분할, 검수 |

| `scripts/` | 우선순위 점수, 실험 표본 크기, PRD 흔적 스캐너 |

원래 작성 지침의 'SYX'는 출처 표시로 남겨 두었습니다. 사례 속 업무 수치는 원래 맥락에만 해당하며 새 프로젝트의 기본 규칙이 아닙니다.

## 보조 스크립트

스크립트에만 Python 3.10 이상이 필요하며 표준 라이브러리만 사용합니다. 입력 형식은 `--help`로 확인하세요.

```bash
python3 scripts/score_priorities.py priorities.csv --method rice
python3 scripts/experiment_math.py --baseline 0.10 --mde 0.02 \
  --alpha 0.05 --power 0.8 --allocation 0.5 --sides two --direction increase
python3 scripts/scan_prd_traces.py PRD.md --allow-codes F-A,Q1 --allow-terms report_id
```

실험 예시는 정규 근사 기준으로 그룹당 3,841, 총 7,682를 출력하며 군집, 순차 검정, 다중 비교, 이탈 보정은 포함하지 않습니다. 트래픽으로 추정한 수집 일수는 완전한 실험 주기를 대체하지 못합니다. 스캐너는 작업 과정의 흔적, 임의로 만든 코드, 영문 식별자, 그리고 페이지를 지정하지 않은 '프로토타입 참고' 같은 맨 참조를 보고합니다. `--unfinished`를 붙이면 자리표시·TODO 표시도 보고합니다. 문서 용어집에 정의된 코드와 확인된 필드는 허용 목록 옵션으로 제외합니다. 발견 위치만 알려 주며, 발견 시 종료 코드는 1입니다.

## 평가와 기여

`evals/evals.json`에는 시나리오 34개가 있으며 V5.0에서 13개를 추가했습니다. 프로토타입 기반 PRD 작성, 프로토타입과 규칙의 충돌, 프로토타입 갱신 동기화, 자산 이름 기록과 재확인, 명확한 변경과 불분명한 변경, 구조적 변경, 새 세션 인수인계, 모듈별 작성, 청사진 우선과 기능 분해 우선, 그 자리 작성과 통합 표의 균형을 다룹니다.

이번 릴리스에서는 시나리오를 실제로 실행했습니다. Kimi K3와 DeepSeek를 피평가 모델로 총 34회 시험 실행했고, 새 시나리오 13개는 1차에 8개를 통과했으며 드러난 문제에 맞춰 규칙을 고친 뒤 13/13을 통과했습니다. 실제 하드웨어 프로젝트의 기능 라인으로 이전·신규 버전 비교도 했습니다. 자세한 과정과 수치는 릴리스 노트에 있습니다. 시나리오 파일만으로 사용자의 클라이언트에서 통과가 보장되지는 않으니, 각자의 환경에서 다시 실행해 보셔도 좋습니다.

Issue와 Pull Request를 환영합니다. 최소 입력, 실제 결과, 기대 결과를 함께 적어 주세요. 공개 가능하거나 익명화한 자료만 사용하고, 실제 고객 데이터·계정 정보·내부 문서는 넣지 마세요. 스크립트를 수정할 때는 실제 실행 결과를, 작성 규칙을 수정할 때는 원래 업무 의미가 유지되는지를 함께 확인해 주세요.
